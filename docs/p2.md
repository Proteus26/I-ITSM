## The report pipeline

`IncidentProcessingPipeline.process(incident, context)` is final and calls, in this order: `suggestCategory`, `classify`,
`prioritise`, `applySla`, `assign`. `StandardIncidentPipeline` implements the steps:

1. **suggest**: only when no category is known. `CategorySuggester` (P5) is asked; a suggestion is used only when its confidence is at least `0.5` (`MIN_SUGGESTION_CONFIDENCE`).
2. **classify**: if a category is known, NEW to CLASSIFIED (actor: system for a report, the administrator for a manual classification). Otherwise the incident stays NEW.
3. **prioritise**: `PriorityService` with impact and urgency weights, `ServiceCatalog.criticalityOf(serviceId)`, affected users and category. Always runs (also for NEW incidents) and runs again after a manual classification. The explanation is stored.
4. **SLA**: `SlaService.computeDeadlines(serviceId, priority, createdAt)`.
5. **assign**: only from CLASSIFIED; `AssignmentService.assign`. No candidate: the incident stays CLASSIFIED and an administrator assigns it.

A new incident always publishes `IncidentReported`. Classification publishes `IncidentClassified` + `StatusChanged`, priority changes
`PriorityChanged` (with the explanation), assignment `IncidentAssigned(strategy)` + `StatusChanged`. System actions have `actorId = null`; a manual assignment has strategy `manual`.
Add a different pipeline by subclassing `IncidentProcessingPipeline` and registering it instead of the standard one.

## Contract highlights (full list in README and Swagger)

- Visibility: reporter, assignee or admin; anybody else gets 403, a missing incident 404. `GET /api/incidents/assigned` is for technicians only (403 otherwise).
- Errors: 400 validation or unknown/inactive service, category or technician; 403 wrong role; 409 impossible lifecycle move or duplicate category; stale save 409.
- `IncidentDetail.actions` (`ACKNOWLEDGE START REQUEST_INFO RESUME RESOLVE VERIFY REOPEN CLOSE CANCEL FEEDBACK ASSIGN CLASSIFY`) and `noteTypes` are computed for the caller.
- Notes: INVESTIGATION by assignee or admin and hidden from employees; INFO_REQUEST only through `request-info`; INFO_RESPONSE by the reporter while PENDING_INFO (or through `resume`); COMMENT by reporter, assignee, admin. Nothing can be added to a CLOSED or CANCELLED incident.
- `resume` by the reporter with a `response` stores an INFO_RESPONSE note; `reopen` and `cancel` store their `reason` as a COMMENT. Notes created by an action publish that action's events, not `NoteAdded`.
- Cancel is possible in NEW and CLASSIFIED only (the lifecycle's rule); reopening clears the resolution and feedback.

## What is left for P2

- Editing an incident (title, description) and attachments are not implemented.
- Cancelling after assignment, a reporter-visible reason for reassignment, and automatic closing of VERIFIED incidents (the state machine already allows `SYSTEM`) have no endpoint or scheduler.
- `GET /api/incidents/mine` has no filters; use `/api/incidents/search` (P4) for that.
- Feedback publishes no event; add one to `IncidentEvent` if notifications should react.
- A confidence threshold or the pipeline order may need tuning with real data; both live in `StandardIncidentPipeline`.
- The demo seeder is a development aid; extend it with more users or incidents as the demo needs.
