## The report pipeline

`IncidentProcessingPipeline.process(incident, context)` is final and calls, in this order: `suggestCategory`, `classify`,
`prioritise`, `applySla`, `assign`. `StandardIncidentPipeline` implements the steps:

1. **suggest**: only when no category is known. `CategorySuggester` (P5) is asked; a suggestion is used only when its confidence is at least `0.5` (`MIN_SUGGESTION_CONFIDENCE`).
2. **classify**: if a category is known, NEW to CLASSIFIED (actor: system for a report, the administrator for a manual classification). Otherwise the incident stays NEW.
3. **prioritise**: `PriorityService` with impact and urgency weights, `ServiceCatalog.criticalityOf(serviceId)`, affected users and category. Always runs (also for NEW incidents) and runs again after a manual classification. The explanation is stored.
4. **SLA**: `SlaService.computeDeadlines(serviceId, priority, createdAt)`.
5. **assign**: only from CLASSIFIED; `AssignmentService.assign`. No candidate: the incident stays CLASSIFIED and an administrator assigns it.

A new incident always publishes `IncidentReported`. Classification publishes `IncidentClassified` + `StatusChanged`, priority changes
`PriorityChanged` (with the explanation), assignment `IncidentAssigned(strategy)` + `StatusChanged`. System actions have `actorId = null`; a manual assignment has strategy `manual`.
Add a different pipeline by subclassing `IncidentProcessingPipeline` and registering it instead of the standard one.

## Contract highlights (full list in README and Swagger)

- Visibility: reporter, assignee or admin; anybody else gets 403, a missing incident 404. `GET /api/incidents/assigned` is for technicians only (403 otherwise).
- Errors: 400 validation or unknown/inactive service, category or technician; 403 wrong role; 409 impossible lifecycle move or duplicate category; stale save 409.
- `IncidentDetail.actions` (`ACKNOWLEDGE START REQUEST_INFO RESUME RESOLVE VERIFY REOPEN CLOSE CANCEL FEEDBACK ASSIGN CLASSIFY EDIT`), `editableFields` and `noteTypes` are computed for the caller.
- Notes: INVESTIGATION by assignee or admin, and visible only to them (relationship-based: a technician who reported the incident does not see them either); INFO_REQUEST only through `request-info` and INFO_RESPONSE only through `resume` (a direct note of either type is 400); COMMENT by reporter, assignee, admin. Nothing can be added to a CLOSED or CANCELLED incident.
- `resume` by the reporter with a `response` stores an INFO_RESPONSE note; `reopen` and `cancel` store their `reason` as a COMMENT. Notes created by an action publish that action's events, not `NoteAdded`.
- Cancel is possible in NEW and CLASSIFIED only (the lifecycle's rule); reopening clears the resolution and feedback and re-arms the SLA (deadlines recomputed from the reopen time). SLA events already recorded stay, and the unique (incident, type) constraint means a breach type recorded before is not recorded again.
- Assignment never picks the reporter: the pipeline excludes them, and an admin assigning to the reporter gets 400. Reassigning to a different technician sends the incident back to ASSIGNED and clears `acknowledgedAt`, so the response SLA applies to the new technician.

## Incident operations (editing, workload, SLA monitor, correlation)

| Endpoint | Who | Notes |
| --- | --- | --- |
| `PATCH /api/incidents/{id}` | reporter, assignee, admin | Partial body: `title`, `description`, `impact`, `urgency`, `affectedUsers`, `serviceId` or `clearService: true`. Reporter: all fields in NEW, CLASSIFIED, ASSIGNED (403 afterwards). Admin: all fields until RESOLVED. Assignee: impact, urgency, affectedUsers, service while active. Resolved or later: 409. A field not allowed: 403. Empty body, bad value, unknown or inactive service: 400. `IncidentDetail.editableFields` lists what the caller may change; `EDIT` is in `actions` exactly then |
| `GET /api/incidents/workload` | technician | Active count against capacity, `overCapacity`, counts per status, `nextDueAt`, and the active incidents by resolution deadline, each `OVERDUE`, `AT_RISK` or `ON_TRACK` with a reason |
| `PATCH /api/me/availability` | technician | `{ "available": true }`; existing assignments stay, only automatic assignment is affected |
| `GET /api/admin/sla/at-risk` | admin | Open incidents that `breached` their SLA or are `atRisk`, each with a `riskReason` (`SlaRiskDetector`: time used against a threshold, nobody has responded, nobody is assigned, assignee over capacity) |
| `GET /api/admin/correlations` | admin | `IncidentCorrelator` clusters: 3 or more open incidents on the same service (or category when there is no service) created in the last 2 hours. Configurable with `itsm.intelligence.correlation.window-minutes` and `.min-size` |
| `GET /api/incidents/{id}/related` | anyone who may see the incident | The cluster the incident is in, with only the members the caller may see; 204 when none |

An edit publishes `IncidentUpdated(changedFields)` inside the transaction (audit `INCIDENT_UPDATED` in the same transaction; notification to the reporter and assignee except the editor, after commit). An edit that changes nothing publishes nothing. When impact, urgency, affected users or service really change, priority is recalculated (`PriorityChanged` if it differs) and the SLA deadlines are recomputed from the original SLA start (re-armed at a reopen), not from the edit time.
Frontend: edit form on the incident page (`intent=edit`), workload card and availability toggle (`intent=availability`) on "Assigned to me", `/admin/sla-monitor`, and "Related incidents" on the detail page.

## What is left for P2

- Attachments are not implemented.
- Cancelling after assignment, a reporter-visible reason for reassignment, and automatic closing of VERIFIED incidents (the state machine already allows `SYSTEM`) have no endpoint or scheduler.
- `GET /api/incidents/mine` has no filters; use `/api/incidents/search` (P4) for that.
- Feedback publishes no event; add one to `IncidentEvent` if notifications should react.
- A confidence threshold or the pipeline order may need tuning with real data; both live in `StandardIncidentPipeline`.
- The demo seeder is idempotent per user and per incident title, logs failures at WARN and continues, and refuses to run under the `prod` profile. It is a development aid; extend it with more users or incidents as the demo needs.
