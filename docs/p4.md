# P4: events, notifications, audit, search and reports

The code lives in `backend/` (packages `audit`, `events`, `notification`, `reference`, `reports`, `search`) and
`frontend/` (notifications, search, admin audit and reports pages, and the notification bell). It is built and tested by CI
with the rest of the app.

## Configuration

All settings are optional; the defaults work with no mail server (emails are written to the backend log).

| Variable | Default | Meaning |
| --- | --- | --- |
| `ITSM_MAIL_GATEWAY` | `logging` | `smtp` sends real email through `MAIL_HOST`/`MAIL_PORT` |
| `ITSM_MAIL_FROM` | `itsm@localhost` | Sender address |
| `ITSM_MAIL_ASYNC` | `true` | Send email on a background pool (tests set `false`) |
| `MAIL_HOST` / `MAIL_PORT` | `localhost` / `1025` | SMTP server (1025 is Mailpit's default) |
| `MAIL_USERNAME` / `MAIL_PASSWORD` | empty | SMTP credentials |
| `ITSM_NOTIFICATION_LINK` | `/incidents/{id}` | Where a notification points |
| `FRONTEND_BASE_URL` | `http://localhost:4321` | Prefix for links inside emails |

To see emails during a demo, run Mailpit (`docker run -p 1025:1025 -p 8025:8025 axllent/mailpit`), set
`ITSM_MAIL_GATEWAY=smtp` and open http://localhost:8025.

`it_services` and `sla_events` are created in a minimal form by `V20261118_1100__sla_reference_tables.sql` so that
search and reports work now; the SLA module (P3) extends them with `alter table`.

### Decision: login audit

`LoginFailed.email` is typed by whoever is at the keyboard, so it is untrusted. Control characters are removed and it is cut to
100 characters before it is stored (as text in `description`; no user id is recorded because the account may not exist). People do
sometimes type a password into the email box, so if that worries you, store only a hash or drop the email and keep just the reason.

## Rules for publishers (P2, P3)

1. Publish `StatusChanged` on **every** status transition; the audit timeline is built from it.
2. Also publish the specific event where one exists (`IncidentAssigned`, `IncidentResolved`, `IncidentClosed`, `IncidentClassified`, `InfoRequested`).
   `RecipientResolver` skips `StatusChanged` for CLASSIFIED / ASSIGNED / RESOLVED / CLOSED so nobody is told twice, so those specific events are what notify people.
3. `actorId` is the user who did it, or `null` for the system.
4. Publish inside the `@Transactional` method. Audit then commits or rolls back with the action; notifications are sent only after commit.

## Definitions

* **Open / active**: `IncidentStatus.OPEN` / `IncidentStatus.ACTIVE`. **Resolved**: RESOLVED, VERIFIED, CLOSED. **Critical**: open P1.
* **SLA breached**: a `RESPONSE_BREACH` or `RESOLUTION_BREACH` row in P3's `sla_events`. **At risk**: open, a `WARNING` row, no breach. **On track**: the rest.
* **SLA compliance**: incidents without a breach / all non-cancelled incidents.
* Dates in search, audit filters and the trend are UTC days (`to` inclusive). Run the database in UTC, or set `hibernate.jdbc.time_zone=UTC`, so the trend's "today" matches.
